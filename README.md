# Market SQL

В папке `solutions/` уже есть файлы для восьми заданий. В каждом напишите SQL-запрос по условию ниже. Для задания 08 также понадобятся файл с индексами и отчёт в конце этого README.

## Запуск и проверка

**1. Откройте базу.** Запустите Docker и откройте терминал в папке с `package.json`. Для команд `npm` нужен Node.js 22+. Первая команда запустит PostgreSQL 16 с учебными данными, вторая откроет его консоль — psql.

```sh
npm run up
npm run sql
```

Когда увидите приглашение `market=#`, введите `\dt market.*`. Должны появиться восемь таблиц. Команда `\d market.payments` покажет колонки таблицы платежей. Если PowerShell блокирует запуск `npm.ps1`, используйте `npm.cmd` вместо `npm`.

**2. Напишите и запустите запрос.** Прочитайте общие правила и задание 01. В редакторе откройте [01_financial_state.sql](solutions/01_financial_state.sql), напишите запрос и сохраните файл. В уже открытой консоли psql выполните две строки ниже. Первая запускает сохранённый файл, вторая возвращает вас в терминал.

```text
\i /work/solutions/01_financial_state.sql
\q
```

**3. Проверьте первую задачу.** В терминале выполните:

```sh
npm run grade -- --task 1
```

При успехе увидите `15/15` за первую задачу. Для следующей замените номер после `--task`. Проверка каждый раз запускает ваш файл на восьми отдельных наборах данных. Например, если ошибка возникла в `checkout`, посмотрите [данные этого набора](database/fixtures/cases/checkout.sql) и [ожидаемые строки](tests/expected/checkout.json). В JSON ключ `"1"` соответствует задаче 01, значения в строке идут в порядке колонок из условия, интервалы указаны в микросекундах.

## Общие правила

Схема таблиц — в [database/schema.sql](database/schema.sql). Все даты и границы периодов считайте в UTC. Каждый файл с запросом должен выполняться самостоятельно и содержать один `SELECT`, при необходимости с `WITH`. Верните колонки с именами и типами из условия, в указанном порядке. Если для строк указана сортировка по полю, используйте порядок по возрастанию, кроме явно указанного `DESC`.

| Показатель | Как считать |
|---|---|
| Стоимость заказа (`order_total`) | Сумма `quantity × unit_price` по позициям заказа. Без позиций — 0 |
| Поступления (`paid_amount`) | Сложите `payments.amount` только для `SUCCESS`. Если у одного заказа несколько успешных платежей с одинаковым `external_transaction_id`, учтите один — самый ранний по `paid_at`, при равенстве с меньшим `id`. Это правило действует и для пустой строки `''`. Каждый платёж с `NULL` учитывайте отдельно. Без успешных платежей — 0 |
| Возвраты (`refunded_amount`) | Сумма `refunds.amount` по заказу. Без возвратов — 0 |
| Чистая оплата (`net_amount`) | Поступления минус возвраты. Может быть отрицательной |
| Что считается покупкой в задачах 03, 06 и 07 | Заказ стоимостью больше нуля, у которого чистая оплата не меньше стоимости и в истории ни разу не было `CANCELLED`. Проверяйте это по всем оплатам и возвратам заказа, даже если они произошли позже отчётного периода |
| Дата покупки | `orders.created_at` |

### 01. Финансовое состояние · 15 баллов

`solutions/01_financial_state.sql` · Таблицы `orders`, `order_items`, `payments`, `refunds`.

Верните одну строку на каждый заказ, включая отменённые и неоплаченные. Отсортируйте по `order_id`.

```text
order_id bigint, order_total numeric, paid_amount numeric, refunded_amount numeric,
net_amount numeric, financial_status text
```

При чистой оплате ≤ 0 статус `UNPAID`. Иначе сравните чистую оплату со стоимостью: меньше — `PARTIALLY_PAID`, равна — `PAID`, больше — `OVERPAID`.

**Пример.** Заказ №1 стоит 100. Сначала пришёл успешный платёж на 120, затем на 150 с тем же идентификатором. Ещё два успешных платежа по 10 имеют `NULL`. Поступления равны 140 (120 + 10 + 10). После возвратов на 1 и 9 остаётся 130. Строка результата — `(1, 100, 140, 10, 130, 'OVERPAID')`.

### 02. Аномалии платежей · 10 баллов

`solutions/02_payment_anomalies.sql` · Таблицы задачи 01 и `order_status_history`.

Верните по одной строке на каждую найденную проблему: `order_id bigint, anomaly_type text`. Один заказ может дать несколько строк с разными типами проблем. Если проблем нет, пропустите заказ. Сортируйте сначала по `order_id`, затем по `anomaly_type`.

| `anomaly_type` | Условие |
|---|---|
| `OVERPAYMENT` | Поступления до возвратов превышают стоимость |
| `EXCESS_REFUND` | Возвраты превышают поступления |
| `AFTER_CANCEL` | Любой исходный `SUCCESS`, включая дубль, пришёл строго позже первой отмены |
| `DUPLICATE_SUCCESS` | В заказе есть два или более успеха с одинаковым идентификатором, отличным от `NULL` |

**Пример.** При стоимости и оплате 50 возврат 60 даёт `(4, 'EXCESS_REFUND')`. Если после отмены пришёл дубль оплаты, добавляются `AFTER_CANCEL` и `DUPLICATE_SUCCESS`.

### 03. Повторная покупка · 10 баллов

`solutions/03_repeat_customers.sql` · `customers` и таблицы для определения покупки.

Для каждого клиента найдите первые две покупки по времени создания заказа. Если время совпало, первым идёт заказ с меньшим `id`. Включите всех клиентов и отсортируйте результат по `customer_id`.

```text
customer_id bigint, first_order_id bigint, second_order_id bigint,
first_purchase_at timestamptz, second_purchase_at timestamptz,
days_between integer, repeated_within_30_days boolean
```

`days_between` — число полных суток между покупками. Для `repeated_within_30_days` сравните точный интервал с 30 сутками. Если у клиента одна покупка, обе колонки второй покупки, число суток и флаг равны `NULL`. Если покупок нет, заполнен только `customer_id`.

**Пример.** Через 30 суток ровно последние два поля равны `30, true`. Через 30 суток и минуту — `30, false`.

### 04. Исторические цены · 10 баллов

`solutions/04_historical_prices.sql` · `orders`, `order_items`, `product_price_history`.

Для каждой позиции найдите последнюю цену товара с `valid_from ≤ orders.created_at`. При равном времени берите запись с большим `id`. Выведите `item_id bigint, unit_price numeric, historical_price numeric, price_status text` по `item_id`.

**Пример.** В момент заказа вступили в силу цены 24 и 25 с id 2 и 3. При цене позиции 25 результат — `(1, 25, 25, 'MATCH')`. При расхождении статус `MISMATCH`. Без подходящей записи — `historical_price = NULL` и `MISSING`.

### 05. Воронка заказа · 15 баллов

`solutions/05_order_funnel.sql` · `orders`, `order_status_history`.

Верните строку на каждый заказ, отсортируйте по `order_id`. Все четыре даты возьмите из `order_status_history.changed_at`. Рассматривайте события по времени, при совпадении — по возрастанию `id`. Найдите первый `CREATED`, после него первый `PAID`, затем `SHIPPED` и `DELIVERED`. Если очередного этапа нет, его дата и все следующие даты равны `NULL`. Повтор более раннего статуса не начинает цепочку заново. `CANCELLED` пропускайте.

```text
order_id bigint, created_at timestamptz, paid_at timestamptz, shipped_at timestamptz,
delivered_at timestamptz, to_paid interval, to_ship interval, to_deliver interval,
late boolean, repeat_count bigint
```

`to_paid`, `to_ship` и `to_deliver` — время между соседними этапами. Если одной из двух дат нет, интервал равен `NULL`. `late` равно `true`, если от отгрузки до доставки прошло больше 72 часов. Без доставки — `NULL`. Для `repeat_count` посчитайте повторы каждого из четырёх статусов по всей истории заказа и сложите их. Без истории — 0.

**Пример.** Для `PAID, CREATED, PAID, SHIPPED, CREATED, DELIVERED` первый `PAID` пропускается, `repeat_count = 2`. Если между отгрузкой и доставкой ровно 72 часа, `late = false`.

### 06. Удержание когорт · 15 баллов

`solutions/06_cohort_retention.sql` · Таблицы для определения покупки.

Когорта — группа клиентов, впервые совершивших покупку в одном календарном месяце. Этот месяц обозначим M0, следующий — M1, ещё через месяц — M2. Используйте покупки с `orders.created_at` строго раньше **1 июля 2024, 00:00 UTC**. Включите группы, у которых к этой дате закончился M2. Например, для апрельской группы M2 — июнь, поэтому она входит в отчёт. Для майской M2 — июль, поэтому она пропускается. Выведите по одной строке на непустую группу, в порядке `cohort_month`.

```text
cohort_month date, cohort_size bigint, m0_retention numeric, m1_retention numeric, m2_retention numeric
```

`cohort_month` — первое число месяца, `cohort_size` — число клиентов. Для каждого месяца M0, M1, M2 разделите число уникальных покупателей когорты в этом месяце на её размер. Округлите доли до шести знаков. Для M2 покупка в M1 необязательна.

**Пример.** Из двух январских клиентов в феврале один купил дважды, а в марте вернулись оба: `('2024-01-01', 2, 1, 0.5, 1)`.

### 07. ABC-анализ · 10 баллов

`solutions/07_abc_analysis.sql` · `products` и таблицы для определения покупки.

Выручка товара — сумма `quantity × unit_price` по позициям покупок. Включите весь каталог. Отсортируйте по `revenue DESC, product_id ASC`.

```text
product_id bigint, revenue numeric, revenue_share numeric, cumulative_share numeric, abc_category text
```

`revenue_share` — выручка товара, делённая на общую выручку. `cumulative_share` — сумма долей от первой строки до текущей включительно в указанном порядке. По точной накопленной доле присвойте категорию: A при доле ≤ 0,80, B при 0,80 < доля ≤ 0,95, иначе C. Округлите обе доли до шести знаков только для вывода. У товара с нулевой выручкой всегда категория C. Если общая выручка равна 0, обе доли у всех товаров равны 0.

**Пример.** Выручки 80, 15, 5 и 0 дают накопленные доли 0,80, 0,95, 1 и 1 и категории A, B, C, C.

### 08. Оптимизация мартовской выгрузки · 15 баллов

`solutions/08_optimized_query.sql` и `solutions/08_indexes.sql` · `products`, `orders`, `order_items`.

Ускорьте [исходный запрос](database/baseline.sql). Для каждого товара верните `product_id bigint, units bigint, gross numeric` по `product_id`. Сложите количество и стоимость позиций **всех** заказов марта 2024 по `created_at`, включая отменённые и неоплаченные.

**Пример.** Две штуки по 10 дают `(202, 2, 20)`. Товар без позиций за март даёт `(201, 0, 0)`.

1. Выполните `npm run perf -- 10000 17`. Команда заменит учебные данные набором на 10 000 заказов. Число 17 — параметр генератора (seed). С теми же двумя числами получится тот же набор.
2. Выполните `npm run plan:before` и сохраните вывод для отчёта. В `08_optimized_query.sql` запишите свой вариант запроса, который возвращает те же строки. В `08_indexes.sql` запишите от 1 до 8 команд `CREATE INDEX`. Используйте обычные B-tree индексы по колонкам таблиц схемы `market`. Допустимы составные индексы, `DESC` и `INCLUDE`.
3. На тех же данных выполните `npm run plan:after`. Индексы создаются на время замера. Обе команды используют `EXPLAIN (ANALYZE, BUFFERS)`.
4. Вставьте оба плана в отчёт ниже. Сравните время выполнения (`Execution Time`) и число блоков данных (`Buffers`), объясните выбор индексов. Затем запустите `npm run grade -- --task 8`: команда проверит строки результата, создание индексов и наличие обоих планов.

## Проверка и сдача

| Команда | Когда использовать |
|---|---|
| `npm run grade` | Проверить все решения перед сдачей |
| `npm run report` | Сохранить результат в `reports/grade.md` |
| `npm test` | Проверить работу самого проверяющего кода и тестовых данных |
| `npm run reset` | Вернуть стартовые данные после экспериментов |
| `npm run down` | Остановить контейнеры |

Автоматически начисляется до 90 баллов. В задаче 08 сверка результатов даёт 2, создание индексов — 2, наличие планов — 1. Ещё 10 баллов даёт отчёт: 3 за разбор исходного плана, 3 за обоснование изменений, 4 за сравнение результата, времени и буферов. Вес каждого сценария виден в выводе проверки.

Для сдачи отправьте ссылку на коммит или pull request с девятью SQL-файлами из `solutions/` и этим README с заполненным отчётом.
